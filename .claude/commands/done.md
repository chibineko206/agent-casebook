案件 `$1` のセッションを終了する。以下を順番に実行する。

引数が空の場合は、このセッションで触った案件を `cases/` と `private/` から推定し、
一意に決まらなければユーザーに確認してから進める。

## 0. 成果物の文書を点検する

このセッションで文書（Markdown / HTML）を作成・更新していれば、
`.claude/commands/doc-check.md` の手順をそのファイルに対して実行し、判定をユーザーに示す。
修正するかはユーザーが決める。文書を作っていなければこの手順は飛ばす。

## 1. 案件を特定する

```
!`cd "$(git rev-parse --show-toplevel)" && ls cases/ private/ 2>/dev/null`
!`cd "$(git rev-parse --show-toplevel)" && git status --short && echo "---" && git log --oneline -3`
```

- 既存の案件なら `cases/<slug>/CASE.md`（または `private/<slug>/CASE.md`）を読む
- **新規案件なら**ディレクトリと `CASE.md` を作る。slug は英小文字・ハイフン区切り、採番しない
- **人事情報・評価に関わる案件は `private/` に置く**（`private/` は `.gitignore` されている）

新規 `CASE.md` のヘッダ:

```markdown
# <案件名>

分類: <運用 / 調査 / 技術検証 / ドキュメント / 学習 など>
状態: 進行中
成果物: <ファイル名。無ければ「なし」>
関連: <Jira キー / 他案件 / なし>
定期作業: <繰り返す作業と周期。無ければ行ごと省く>
```

## 2. CASE.md にエントリを追記する

**末尾に追記する。過去のエントリは書き換えない。**
セッション中の実際の作業に基づいて書き、推測で埋めない。

```markdown
---

## <YYYY-MM-DD> [Code] <このセッションの要約>

### やったこと
### 判断
### 未決事項
```

- モードは `[Code]` / `[チャット]` / `[Cowork]`。このコマンドから実行する場合は `[Code]`
- **やったこと**: 変更したファイルと、それが何を実現したか。前回の未決を「やった・確かめた」で閉じたものは結果をここに書く
- **判断**: 選択肢があった箇所で何を選び、なぜそうしたか。**見送った案も残す**。前回の未決を「やらない」で閉じたものは理由をここに書く
- **未決事項**: 下の定義に従い、前回分を閉じたうえで**全量を書き直す**。無ければ「なし」と書く

数週間後に「以前決めた内容から仕様変更したい」と戻ってきたとき、
この 3 節だけで再開できるかを基準に書く。

### 未決事項の定義

未決事項とは、この案件を終えるために誰かがまだ「決める・やる・確かめる」必要があることで、
担当と次の動きが書けるもの。

- **決める**: 選択肢があり、まだ選んでいない
- **やる**: 作業として残っている
- **確かめる**: 前提にしたが裏を取っておらず、結果次第で成果物が変わるもの

「待ち」は種類ではなく状態。3 種類のどれかに「誰を待っているか」を添える。

未決に**含めない**ものと、その置き場:

- **定期作業**（月次・週次の集計など）→ ヘッダの `定期作業` 行。未決にも問答にも出さない。
  ユーザーが「今回分を管理して」と明示したときだけ未決に書く。
  定期作業の初回や、繰り返しの形を変える 1 回限りの変更は単発なので未決に書く
- 結果で成果物が変わらない未確認事項 → 判断節に「〜は確認せず進めた（理由）」と書いて閉じる
- 既知の限界、受け入れた制約 → 判断節。二度と未決に書かない
- 他案件の話 → その案件の `CASE.md` に書き、こちらは判断節に「〜案件へ移した」と書いて閉じる

線引きは「それが終わっても、また同じ作業が来るか」。来るなら定期作業、来ないなら未決。

### 前回の未決事項を閉じる（問答）

前回エントリの未決事項を 1 件ずつ列挙し、このセッションの内容から
「やった / やらない / 残す」を推定して添え、ユーザーに確認する。違う項目だけ直してもらう。

```
前回の未決事項 3 件。「やった / やらない / 残す」で答えてください。
1. 決める: current.sql と paid-only.sql のどちらを本番にするか
   → 今回の作業から「やった（paid-only に決定）」と推定
2. やる: 提案ブランチの取り込み可否（メンバー待ち、期限 10/9）
   → 期限切れ。残すなら次の動きを伺う
3. 確かめる: 別環境でも同じ不具合が出るか
   → 今回触っていない。「残す」と推定
```

閉じ方は 3 つだけ:

- **やった・確かめた** → 未決から消し、やったこと節に結果を書く
- **やらない** → 未決から消し、判断節に理由を書く。「いつかやる」「余裕があれば」のように
  契機（日付か条件）が書けないものはこれにする
- **残す** → 種類・担当・次の動き（日付か条件）を付けて書き直す。「やる」と決めただけでは閉じない

期限を過ぎた待ちは必ず問い直す。
新しい未決は、このセッションで分かった「決めていない・やっていない・確かめていない」のうち
成果物に影響するものだけを足す。

書式:

```markdown
### 未決事項
- 決める: current.sql と paid-only.sql のどちらを本番にするか。自分、次回セッション
- やる: 提案ブランチの取り込み可否。メンバー待ち、回覧済み、期限 10/9
- 確かめる: 別環境でも同じ不具合が出るか。自分、次回の検証で
```

「前エントリの未決は継続」のような参照は書かない。最新エントリの未決事項が常に全量になるようにする。
10 件を超えたら案件の切り方を疑う。

## 3. メタ情報を更新する

`CASE.md` ヘッダの `状態` と `成果物` を実態に合わせる。状態は未決事項から導く。

- 未決がなく、成果物を渡し終えた → `完了`
- 未決が他者待ちだけ → `保留`
- それ以外 → `進行中`

定期作業がある案件はヘッダに `定期作業` 行を足す
（例: `定期作業: 毎月月初に月次集計を実行（手順は README.md）`）。

## 4. INDEX を更新する

- `cases/` の案件 → `INDEX.md`
- `private/` の案件 → `private/INDEX.md`

該当行の `状態` と `更新` を直す。行が無ければ追加する。

更新後に `python3 tools/dashboard.py --html` を実行し、ダッシュボード（`.tmp/dashboard.html`）を最新にする。
失敗しても手順は止めず、報告に含める。

## 5. コミットする

他案件の未コミット変更が残っていることがあるため、**この案件のファイルだけ**を対象にする
（`git add -A` は使わない）。運用そのものを扱う案件で `CLAUDE.md` や `.claude/` や `tools/` を触ったときは、それらも add する。

```
git add cases/<slug> INDEX.md
git commit -m "<slug>: <このセッションの要約>"
```

`private/` の案件は `.gitignore` されているため、コミット対象が無いのが正しい。
その場合は手順 5 を飛ばし、飛ばしたことを報告に含める。

push は行わない。必要ならユーザーが判断する。

## 6. 報告する

`CASE.md` のパス、追記したエントリの見出し、コミットハッシュを 1 行ずつ示す。
失敗した手順があれば、成功した手順と併せて明示する（黙って飛ばさない）。
