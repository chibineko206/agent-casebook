案件 `$1` のセッションを終了する。決定的な処理（案件の特定、前回の未決の抽出、追記、ヘッダと INDEX の更新、
ダッシュボード再生成、コミット）は `tools/casebook.py` が行う。cwd に依存しないので、どこから実行してもよい。
Skill がやるのは、判断と文章だけ。

スクリプトのパスはリポのルートからの相対で `tools/casebook.py`。cwd がルートでなければ
`"$(git rev-parse --show-toplevel)/tools/casebook.py"` と書く。

## 1. 現状を出す

```
python3 tools/casebook.py start $1
```

案件の所在、ヘッダ、最新エントリ、前回の未決事項（種類・待ち・期限切れ付き）、git の状態が出る。

- 引数が空のときは `start` を引数なしで実行し、一覧からこのセッションで触った案件を推定する。一意に決まらなければユーザーに確認する
- 案件が無ければ新規。`python3 tools/casebook.py new <slug> --title "<案件名>" --category <分類> [--artifacts "<成果物>"] [--related "<関連>"] [--periodic "<定期作業>"]` で作る。
  slug は英小文字・ハイフン区切りで採番しない。**人事情報・評価に関わる案件は `--private`** を付ける（`private/` は gitignore 済み）

## 2. 成果物の文書を点検する

このセッションで文書（Markdown / HTML）を作成・更新していれば、`.claude/commands/doc-check.md` の手順を
そのファイルに対して実行し、判定をユーザーに示す。修正するかはユーザーが決める。文書を作っていなければ飛ばす。

## 3. 前回の未決事項を閉じる（問答）

`start` が出した前回の未決事項を 1 件ずつ列挙し、このセッションの内容から「やった / やらない / 残す」を
推定して添え、ユーザーに確認する。違う項目だけ直してもらう。

```
前回の未決事項 3 件。「やった / やらない / 残す」で答えてください。
1. 決める: current.sql と paid-only.sql のどちらを本番にするか
   → 今回の作業から「やった（paid-only に決定）」と推定
2. やる: 提案ブランチの取り込み可否（メンバー待ち、期限 10/9）
   → 期限切れ。残すなら次の動きを伺う
3. 確かめる: 別環境でも同じ不具合が出るか
   → 今回触っていない。「残す」と推定
```

閉じ方は 3 つだけ。

- **やった・確かめた** → 未決から消し、やったこと節に結果を書く
- **やらない** → 未決から消し、判断節に理由を書く。「いつかやる」「余裕があれば」のように契機（日付か条件）が書けないものはこれにする
- **残す** → 種類・担当・次の動きを付けて書き直す。「やる」と決めただけでは閉じない

期限を過ぎた待ちは必ず問い直す。

## 4. エントリを書く

`.tmp/done-entry.md`（gitignore 済み）に、次の形で書く。セッション中の実際の作業に基づき、推測で埋めない。

```markdown
## <YYYY-MM-DD> [Code] <このセッションの要約>

### やったこと
### 判断
### 未決事項
```

- モードは `[Code]` / `[チャット]` / `[Cowork]`。このコマンドから実行する場合は `[Code]`
- **やったこと**: 変更したファイルと、それが何を実現したか。前回の未決を「やった・確かめた」で閉じたものは結果をここに書く
- **判断**: 選択肢があった箇所で何を選び、なぜそうしたか。**見送った案も残す**。前回の未決を「やらない」で閉じたものは理由をここに書く
- **未決事項**: 前回分を閉じたうえで**全量を書き直す**。各行は `- 決める: ` `- やる: ` `- 確かめる: ` のどれかで始め、担当と次の動き（日付か条件）を添える。無ければ `- なし`

数週間後に「以前決めた内容から仕様変更したい」と戻ってきたとき、この 3 節だけで再開できるかを基準に書く。

### 未決事項の定義

未決事項とは、この案件を終えるために誰かがまだ「決める・やる・確かめる」必要があることで、担当と次の動きが書けるもの。

- **決める**: 選択肢があり、まだ選んでいない
- **やる**: 作業として残っている
- **確かめる**: 前提にしたが裏を取っておらず、結果次第で成果物が変わるもの

「待ち」は種類ではなく状態。3 種類のどれかに「誰を待っているか」を添える。

未決に**含めない**ものと、その置き場:

- **定期作業**（月次・週次の集計など）→ ヘッダの `定期作業` 行。ユーザーが「今回分を管理して」と明示したときだけ未決に書く。定期作業の初回や、繰り返しの形を変える 1 回限りの変更は単発なので未決に書く
- 結果で成果物が変わらない未確認事項 → 判断節に「〜は確認せず進めた（理由）」と書いて閉じる
- 既知の限界、受け入れた制約 → 判断節。二度と未決に書かない
- 他案件の話 → その案件の `CASE.md` に書き、こちらは判断節に「〜案件へ移した」と書いて閉じる

線引きは「それが終わっても、また同じ作業が来るか」。来るなら定期作業、来ないなら未決。
「前エントリの未決は継続」のような参照は書かない（スクリプトが警告する）。10 件を超えたら案件の切り方を疑う。

## 5. 締める

```
python3 tools/casebook.py finish $1 --entry .tmp/done-entry.md [--state <進行中|保留|完了>] [--artifacts "<成果物>"] [--also <パス> ...]
```

- `--state` は未決事項から導く。未決がなく成果物を渡し終えた → `完了`、未決が他者待ちだけ → `保留`、それ以外 → `進行中`（変わらなければ省く）
- `--artifacts` はヘッダの `成果物` を実態に合わせるときだけ
- `--also` は、この案件で `CLAUDE.md` や `.claude/` や `tools/` などの仕組みのファイルを触ったときに、それらを同じコミットに含めるために使う。他案件の未コミット変更は巻き込まない（スクリプトは `cases/<slug>` と `INDEX.md` しか add しない）
- スクリプトは書式を検査してから追記し、ヘッダと INDEX を更新し、ダッシュボードを再生成し、コミットする。書式エラーが出たらエントリを直して再実行する
- `private/` の案件はコミット対象が無いのが正しい。スクリプトがそう報告する
- push は行わない。必要ならユーザーが判断する

## 6. 報告する

スクリプトの出力をもとに、`CASE.md` のパス、追記したエントリの見出し、コミットハッシュを 1 行ずつ示す。
失敗した手順があれば、成功した手順と併せて明示する（黙って飛ばさない）。
