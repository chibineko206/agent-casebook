# Claude 運用設計

作成: 2026-09-09（claude.ai チャットでの検討結果を集約）
改訂: 2026-09-09（実際の困りごとを整理し、issue ベースから案件ベースに変更）
経緯: 運用を扱う案件の `CASE.md`（例: `cases/casebook-ops/CASE.md`）

## 1. 背景・課題

チャット / Cowork / Code を併用して日々多数の相談と作業をしている。作業の幅は広い。

- 課の目標管理・評価・各種ドキュメント作成
- 製品 X（共通基盤）の調査と作業計画
- MOC 作成
- 技術検証
- 各種ドキュメント作成
- BigQuery での集計クエリ作成・調整

各ツールのコンテキスト（チャットの Project、Cowork のプロジェクト、Code の CLAUDE.md）は
相互に同期されないため、記録を Claude の中ではなく全ツールが読み書きできる場所に置く必要がある。

### 解決したい迷子（設計の判断基準）

次の 3 つが**同じ場所で解けない**ときに迷子になる。この 3 つを 1 箇所で解けるかが判断基準。

1. あの作業、どこでいつ相談したっけ
2. 成果物どこだっけ
3. 以前決めた内容から仕様変更があるので、成果物を更新したい

### 前提

- ローカルの個人利用。会社への共有展開は考えない
- 管理さえできれば、GitHub issue やリポジトリという手段にはこだわらない

## 2. 決定事項

| 項目 | 決定 | 理由 |
|---|---|---|
| 置き場 | GitHub リポジトリ `agent-casebook`（Private） | 3 ツールとも到達可能。ローカルで完結し、バックアップも兼ねる |
| **記録の単位** | **案件**（セッションではない） | 探すときの単位が案件だから。セッション単位だと同じ案件が時期ごとに散って迷子が再発する |
| 器 | `INDEX.md`（一覧）と `cases/<slug>/`（案件）の 2 つだけ | 器が増えると一元管理という目的に反する |
| 案件ファイル | `cases/<slug>/CASE.md` にメタ + 時系列ログ。末尾に追記し過去は書き換えない | 再訪時に「いつ・どのモードで・何を決めたか」が 1 ファイルで読める |
| 採番 | しない。ディレクトリ名は slug のみ | 採番待ちが「まず起票」の摩擦になる |
| 成果物 | `CASE.md` と同じディレクトリに置く | 「成果物どこだっけ」を構造で解決する |
| GitHub issue | **使わない** | issue の価値は共有・状態管理・通知。ローカル個人利用ではどれも不要 |
| 人事情報 | `private/` に置き `.gitignore` する。**場所で分ける** | ファイル名で判定すると命名ミスで漏れる。会社 Org へ移すと Private でも Org admin が閲覧できるため、その保険にもなる |
| 検索 | `grep -ril <語> cases/ private/` | `.gitignore` は git の話なので grep は両方を横断する。検索が分断されない |
| 別リポを作る判定 | **「そのコードを半年後も動かし続けるか」の 1 問だけ** | 使い捨ての検証コードは、コードがあってもリポを作る理由にならない |
| 書き戻しの手段 | `/done <slug>`（`.claude/commands/done.md`） | 手順をコマンドに埋め込まないと形骸化する |
| ルール階層 | 個人共通 `~/.claude/CLAUDE.md` → 管理リポ `CLAUDE.md` → 作業リポ `CLAUDE.md` | Code の階層読み込みに沿う |
| 各階層の担当範囲 | 個人共通 = 全リポ共通の作法／管理リポ = このリポの運用手順／作業リポ = 技術規約 | 同じ事柄を複数階層に書かず矛盾を防ぐ（詳細な表は管理リポ `CLAUDE.md` を正とする） |
| Jira との関係 | チーム共有・監査が必要なものは Jira を正とし、`CASE.md` の `関連` に Jira キーを併記 | 二重管理を避ける |

## 3. 検討して見送った案

### 記録方式

- **1 issue = 1 セッション（issue ベース運用）**: 当初これで実装したが、記録がセッション単位に切れるため
  「以前決めた内容から更新したい」で毎回探し直しになる。迷子の直接の原因だった
- **相談ごとに issue を切る**: 起票の正が Code なので、チャットの現場から書けず溜め込みになる
- **常設の相談 issue にコメントを積む**: GitHub 検索はコメント単位で絞れず、年 250 件規模で破綻する。
  ローカル grep も効かない
- **相談ログを別ファイルに持つ（`docs/log/YYYY-MM.md`）**: 記録先が増え、一元管理という目的に反する
- **段階 0 / 1 / 2 と昇格ルール**: 入口で判定できず「後から昇格」が前提になっていた。判定が要らない設計にした
- **セッション transcript へのポインタ（`claude --resume`）**: 保持の保証がなく端末を変えると失われる。
  長いセッションの丸ごと復元は無関係な文脈も載るため、成果物を読ませる方が速い
- **`TASKS.md` の手書き維持**: 案件一覧と同じ情報の手書きコピーになるため `INDEX.md` 1 つに統合

### 置き場

- **Jira をメインにする**: チーム運用には最適だが、個人の Claude 運用記録としては重い。将来チーム展開時に再検討
- **Linear**: コネクタは安定しているが新規ツール導入が必要
- **親フォルダ方式（全リポを 1 フォルダ配下に置き、そこで Code 起動）**: 横断調査時のみ使う。常用するとコンテキストを食う
- **人事情報を別リポにする**: `grep` が横断できなくなり検索が分断される。同一リポ内の `private/` で足りる

## 4. 各ツールの役割分担

| ツール | 役割 |
|---|---|
| チャット | 新規課題の壁打ち。ローカルファイルを触れないため、結果は Code / Cowork 側で `CASE.md` に書き戻す |
| Cowork | 調査・文書作成。ローカル clone を開いて作業し、`CASE.md` に書き戻し |
| Code | 案件の作成・更新、`/done` による書き戻し、対象リポでのブランチ / PR |

## 5. 懸念事項

- 上位 / 下位 CLAUDE.md の矛盾 → 役割を分け、同じ事柄を両方に書かない
- CLAUDE.md は強制ではない → 絶対に止めたい操作は PreToolUse hook で。
  ただし `private/` は `.gitignore` で足りるため現時点では hook を作らない（`git add -f` を叩かない限り不要）
- 書き戻しの形骸化 → `/done` に手順を埋め込んで定着させる
- チャットからは `CASE.md` を直接書けない → 相談を Code 側に寄せるか、思い出したときにまとめて書き戻す
- 人事情報のバックアップが無い → push しない以上 Time Machine 等に依存する
- claude.ai / Cowork の GitHub コネクタは接続済みでもツールが出ない等の報告が 2026 年に複数ある

## 6. 未決事項

- `INDEX.md` は手書き。案件が 10 件を超えたら `CASE.md` のメタから生成する

## 7. 現在の構成（2026-10-15 時点）

```
CLAUDE.md           毎回効かせる制約だけ（解説はマニュアル、固有規則は .claude/rules/）
INDEX.md            案件一覧
cases/<slug>/       案件ごとの作業場
    CASE.md         メタ情報 + セッションごとの時系列ログ（やったこと / 判断 / 未決事項）
    <成果物>
private/            人事情報など push しない案件。.gitignore 済み
docs/               このマニュアルと設計メモ
.claude/settings.json   hook の登録
.claude/hooks/      SessionStart（進行中の案件と前回の記録漏れを表示、ダッシュボード更新、セッション登録）
                    SessionEnd（記録漏れの検知、セッション登録の削除）
                    session-start.local.sh があれば利用側の表示を足す（同期対象外）
.claude/rules/      利用側の固有の規則（同期対象外）
.claude/commands/   /done（tools/casebook.py を呼び、判断と文章だけを担う）、/doc-check
tools/              dashboard.py（単一 HTML のダッシュボード）、casebook.py（/done の決定的処理）、
                    launcher/（casebook:// を受ける macOS アプリ）、check-public.sh（公開前点検）
templates/          ~/.claude/CLAUDE.md と /writeback の雛形
```

仕組みの正はこのリポで、日々使うリポは取り込むだけ（`docs/001-maintenance.md`）。
