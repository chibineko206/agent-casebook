運用マニュアル

Claude（チャット / Cowork / Code）での相談と作業を、案件単位で 1 箇所に溜めるための手順書。ローカルの個人利用が前提で、チームへの共有展開は想定しない。

これは何のためにあるか

解決したいのは次の 3 つ。これが同じ場所で解けないときに迷子になる。

困ること答えの在処
あの作業、どこでいつ相談したっけ CASE.md の見出しが日付とモード（[Code] / [チャット] / [Cowork]）になっている
成果物どこだっけ CASE.md と同じディレクトリの中
以前決めた内容から仕様変更したい 同じ CASE.md に過去の判断が時系列で残っている。読ませて成果物を更新し、末尾に 1 エントリ足す

守るべき原則はひとつだけ

記録の単位は案件。セッションではない。同じ案件を数週間後に再訪しても、新しい場所を作らず同じ CASE.md に追記する。ここを崩すと、ひとつの案件が時期ごとに散って迷子が再発する。

ケース別の対処

日常で出会う 8 つの場面をどう扱うか。詳細は各節にあるが、まずここだけで動ける。

新規に相談する

何を始めるか言うだけ。mkdir も採番も不要で、相談だけで終わるなら何も作られない。成果物が出た時点か /done を打った時点で Claude が cases/<slug>/ を作る。人事・評価に関わるなら、そう伝えれば private/ に置かれる。手順は案件の進め方。

相談を途中で中断する

中断もセッションの終わりとして扱い、離れる前に /done <slug> を打つ。結論が出ていなくてよい。「どこまで進んだか」「次に何をするか」を未決事項に残すのが目的で、これさえあれば再開の操作は期間によらず同じになる（次項）。

急な離席で打てなかったときは、未コミットの変更が残っていれば次回起動時に「前回 /done していません」と出るので、そこで書き戻す。

中断した相談から再開する

中断時に /done してあれば、短期でも長期でも操作は同じ。新しいセッションで CASE.md を読ませて続きを頼む（過去の相談に戻ると同じ手順）。

/done せずに中断してしまった場合だけ、期間で操作が分かれる。

  • 短期（同じ端末で、当日〜数日内） — claude --continue（直近のセッションを再開）で中断地点から続けてよい。「セッションを再開しない」原則は記録済みの相談に戻る場合の話で、まだ何も記録していない中断セッションは対象外。戻ったら、続ける前にまず現在地を /done で記録しておくと二度目の中断に耐える
  • 長期（記憶が薄い、または端末が違う） — セッション履歴は当てにしない。残っているファイルと git の状態から Claude に現状を整理させ、思い出せる判断を CASE.md に追記してから続ける

過去の相談を探して、再開する

うろ覚えの単語で探させ、CASE.md を読ませ、続きを頼む。3 ステップの詳細は過去の相談に戻る。新しい案件は作らず、同じ CASE.md の末尾に追記していく。

集計クエリの案件を探して

過去の相談を参考にして、新規に相談する

参考元の CASE.md を読ませてから、「これは新しい案件」と明示して始める。明示しないと Claude が既存案件の続きと判断し、参考元の CASE.md に追記されてしまう。

cases/bq-sales-agg/CASE.md を読んで。
これを参考に、新しく解約率の集計を作りたい

新しい案件の CASE.md ヘッダの「関連」に参考元の slug を書いておくと、後から逆向きにも辿れる。

続きか新規か迷ったら判定は 1 つ: 同じ成果物を更新するなら続き、別の成果物が生まれるなら新規。

管理リポ外での相談をここに移行する

すでに別の場所でやってしまった相談を取り込む。どこでやったかで 2 つに分かれる。

  • チャット / Cowork での相談 — その場で「CASE.md 用のエントリを Markdown で出して」と言わせて手元に持ち、Code で該当案件（無ければ新規）に貼って追記する。エントリの日付は相談した日、モードは [チャット] / [Cowork] のまま書く
  • 別リポやリポ外での Code セッション — そのセッションの終わりにユーザー共通コマンド /writeback <slug> を打つ。~/agent-casebook を絶対パスで更新するので折り返しは要らない。コードが保守対象ならそのリポに置いたままにし、CASE.md にはリポ / ブランチ / PR を記録するだけ（別リポを作る判定と同じ扱い）。使い捨てなら成果物ごと cases/<slug>/ に移す

チャットや Cowork からの移行はあくまで救済で、モードの使い分けのとおり、記録したい相談は最初から Code とこのリポで始める。別リポでの作業が前提の案件は例外で、そのセッションの終わりに /writeback を打つのが正規の手順になる。

手元のファイルを持ち込む

相談中にこのリポの外にあるファイルを参照したら、Claude がその場で置き場所を提案する。基本は cases/<slug>/ への移動で、元の場所には残さない。シンボリックリンクは git がリンク先のパスしか記録せず grep -r も辿らないため、二重管理の解消にならない。移動は元の場所からファイルが消えるので、許可を得てから行う。

  • 相談のために用意した資料（仕様書・下書き・スクリーンショット） — cases/<slug>/ へ移動
  • 別のツールが固定パスで読む設定ファイル（~/.claude/commands/writeback.md など） — 実体を cases/<slug>/ に置き、元の場所にリンクを張る。リンクを認めるのはこのケースだけ
  • 保守対象の別リポに属するファイル — CASE.md にパス・ブランチ・PR を記録するだけ
  • 動画や大きなログ、他人の管理物 — CASE.md に所在を記録するだけ
  • 人事情報を含むもの — 上のいずれでも置き先は private/<slug>/

投稿記事を書く

「〜の記事を書きたい」と言えば、Claude が article-<題材> の案件を分類「記事」で起票する。記事 1 本につき 1 案件で、相談の管理フォルダを別に作ったり、その下に記事ごとのフォルダを切ったりはしない（構造の「1 階層」の原則）。記事の一覧は INDEX.md の分類「記事」か ls cases/ | grep article- で得る。

  • 本文の下書き — article.md。冒頭に読み手・目標規定文・投稿先を書く
  • 壁打ちログ — chat-log/YYYY-MM-DD-<ツール名>.md。出典として残し、書き換えない
  • 投稿先と投稿日 — 投稿したら CASE.md の「関連」とエントリに記録する
  • 記事をまたいで使うもの（投稿先ごとの書式、読み手の想定、過去記事の一覧） — 案件ではなく docs/ に置く

分担

ディレクトリの作成、slug の決定、成果物の保存先はすべて Claude が行う。mkdir も採番も不要。

あなたがやること
  1. 何を始めるか言う
  2. 人事・評価の案件なら、そう伝える
  3. 終わりに /done を打つ

加えて判断そのもの（何を選び、なぜそうするか）はあなたが決める。Claude はそれを CASE.md に書き留めるだけ。

構造

器は INDEX.md と cases/ の 2 つだけ。器を増やすと一元管理という目的に反する。

INDEX.md            案件一覧（push する）
cases/<slug>/       案件ごとの作業場（push する）
    CASE.md         メタ情報 + セッションごとの時系列ログ
    <成果物>        クエリ・文書・検証コードなど
private/            人事情報など push しない案件。.gitignore 済み
    INDEX.md
    <slug>/CASE.md
docs/               案件をまたいで参照する設計メモとこのマニュアル
.claude/hooks/      SessionStart / SessionEnd hook（session-start.local.sh があれば利用側の表示を足す）
.claude/rules/      利用側の固有の規則（CLAUDE.md と同じ優先度で毎回読まれ、仕組みの更新で上書きされない）
.claude/commands/   カスタムコマンド（/done, /doc-check）
tools/              ダッシュボード生成（dashboard.py）と Launcher（launcher/）
~/.claude/commands/writeback.md
                    ユーザー共通コマンド /writeback（templates/writeback.md を置く）

ディレクトリ名は slug のみで、番号を振らない。採番を待つ手間がそのまま「まず起票」の摩擦になり、記録しなくなる原因になるため。

cases/ は 1 階層で、分類ごとのフォルダ（例: cases/articles/<slug>/）は作らない。hook と /done が cases/*/CASE.md の 1 階層だけを探すため、入れ子にした案件は起動時の表示と /done 漏れの検知から外れる。案件の種類は INDEX.md の分類列と slug の接頭語で表し、ls cases/ | grep article- のように絞る。

決まっている接頭語は次のとおり。app- のような製品名・サービス名は対象の名前であって、接頭語の規則ではない。

接頭語分類使い方
article-記事社内などへ投稿する記事。記事 1 本につき 1 案件とし、題材を続ける（例: article-agile-estimation）。本文の下書きは article.md、執筆前に AI と壁打ちしたログは chat-log/ に YYYY-MM-DD-<ツール名>.md で置く。投稿先の書式など記事をまたいで使うものは docs/ に置く

GitHub issue は使わない。issue の価値は共有・状態管理・通知だが、ローカルの個人利用ではどれも要らない。

なぜセッションを再開しないのか

  • 保持が保証されない。端末を変えれば失われる
  • チャットと Cowork の履歴は Code から辿れない。戻り方がモードごとに変わってしまう
  • 重い。長いセッションを丸ごと復元すると無関係な文脈も全部載る。数時間の議論が 2 MB になることもある。CASE.md を読ませた方が速く、必要な部分だけが載る
  • 必要な情報は CASE.md にある。判断と見送った案を残しているのは、まさにこのためである

この仕組み自体に問題が出たとき

運用の不具合も案件として扱う。運用を扱う案件（例: cases/casebook-ops/CASE.md）に判断の理由と未決事項が並んでいるので、新しいセッションで読ませてから症状を伝える。

cases/casebook-ops/CASE.md を読んで。hook が起動時に表示されなかった

これで足りるなら、それ自体がこの仕組みが機能している証拠になる。足りなければ CASE.md に書くべき情報が漏れていたということなので、その漏れも追記する。

private/ の扱い

人事情報・評価は private/ に置く。.gitignore されているのでリモートには出ない。

ファイル名ではなく置き場所で判断する。命名規則で分けると、名前を間違えた 1 件が漏れる。ディレクトリを間違えなければ漏れない。

会社 Org へリポジトリを移すと、Private のままでも Org の owner / admin は中身を閲覧できる。private/ はその保険にもなっている。

検索は分断されない

.gitignore は git の話なので、grep は cases/ と private/ を横断する。人事案件を別リポに切り出すとこれができなくなるため、同一リポ内に置いている。

  • バックアップが無い。push しない以上、Time Machine 等に依存する
  • 案件名を漏らさないため INDEX.md は 2 つに分けている（private/INDEX.md 側も push されない）

モードの使い分け

記録が残るのは Code だけ。ここを間違えると、解決したはずの迷子が戻ってくる。

原則

記録したい相談は Code でやる。チャットと Cowork は壁打ちに限り、結論が出そうになったら Code に移す。

モードごとにできること

モードCASE.md/donehook忘れたら
Code書ける使える効く次回起動時に「前回 /done していません」と出る
Cowork書けるコマンドとしては使えない効かない気づく手がかりなし
チャット書けない使えない効かない記録ゼロ。手がかりなし
別リポ / リポ外で開いた Code書ける代わりに /writeback <slug>効かない気づく手がかりなし

それでもチャットや Cowork を使うとき

  • Cowork は実質使える。/done の実体は .claude/commands/done.md というただの Markdown なので、「このファイルの手順どおりに記録して」と言えば同じ結果になる
  • チャットは折り返す。相談の終わりに「CASE.md 用のエントリを Markdown で出して」と言わせて手元に持ち、次に Code を開いたときに貼る
  • 別リポやリポ外で開いた Code は /writeback <slug>。ユーザー共通コマンド（templates/writeback.md を ~/.claude/commands/writeback.md に置く）なので、どのディレクトリで開いた Code でも使える。/done との違いは、エントリに 作業場所: の行が付くことと、コミット対象がその案件のファイルだけに絞られること。作業中のリポには何も書かない
注意

hook は Claude Code だけの機能なので、他モードで進めた分は Code 側から検知できません。SessionStart が「14 日以上更新なし」を出すので気づきやすくはなりますが、検知ではありません。

はい

cases/<slug>/ の中で完結させる。技術検証の使い捨てコードもここに置く

## 2026-10-15 [チャット] 税込対応の仕様変更

### やったこと
- query.sql を税抜 → 税込に変更

### 判断
- 端数は切り捨て。経理の既存処理に合わせた
- 却下: 四捨五入（既存レポートと差分が出る）

### 未決事項
- やる: 過去分の再集計。自分、次回セッション
- 確かめる: 経理側の丸め処理が本当に切り捨てか。経理担当待ち

3 つの節の役割

  • やったこと — 変更したファイルと、それが何を実現したか
  • 判断 — 何を選び、なぜそうしたか。見送った案も残す。仕様変更のときに一番効くのがここ
  • 未決事項 — この案件を終えるために、まだ誰かが「決める・やる・確かめる」必要があること。前回分を閉じたうえで全量を書き直す。無ければ「なし」と書く

書く量の基準は、数週間後にこの 3 節だけを読んで再開できるか。それ以上は書かなくてよい。

未決事項の定義と閉じ方

未決事項は 3 種類だけ。決める（選択肢があり、まだ選んでいない）、やる（作業として残っている）、確かめる（前提にしたが裏を取っておらず、結果次第で成果物が変わる）。「待ち」は種類ではなく状態で、誰を待っているかを添える。1 件ごとに種類・担当・次の動き（日付か条件）を書く。

閉じ方も 3 つだけ。やった（やったこと節に結果を書く）、やらない（判断節に理由を書く）、残す（書き直して次のエントリへ）。「やる」と決めただけでは閉じない。「いつかやる」のように契機が書けないものは「やらない」で閉じ、必要になったらそのとき未決に戻す。/done は前回の未決を 1 件ずつ出し、セッションの内容から推定を添えて「やった / やらない / 残す」を聞く。

未決に含めないものは 4 つ。線引きは「それが終わっても、また同じ作業が来るか」。

  • 定期作業（月次・週次の集計など） — ヘッダの 定期作業 行に書き、明示的に管理を頼まれたときだけ未決に出す。初回や、繰り返しの形を変える変更は単発なので未決に書く
  • 結果で成果物が変わらない未確認事項 — 判断節に「確認せず進めた」と理由を書いて閉じる
  • 既知の限界、受け入れた制約 — 判断節に書く
  • 他案件の話 — その案件の CASE.md に書き、こちらは「〜案件へ移した」で閉じる

「前エントリの未決は継続」のような参照は書かない。最新エントリの未決事項が常に全量で、ヘッダの 状態 はそこから導く（未決がなく成果物を渡し終えたら完了、他者待ちだけなら保留、それ以外は進行中）。

セッションの記録に頼らない

セッションの会話履歴には頼らない。保持は保証されず、端末を変えれば失われる。チャットと Cowork の履歴は Code から辿れない。だから結論は CASE.md に自分の言葉で書く。戻り方は過去の相談に戻るを参照。

ルールの階層

Code は上位から順に読み込む。同じ事柄を 2 箇所に書くと矛盾するので、役割を分ける。

階層置くもの
~/.claude/CLAUDE.md全リポ共通の作法・原則（応答は日本語、外向きの操作は事前確認）
agent-casebook/CLAUDE.mdこのリポの運用手順（cases/ の切り方、/done、private/ の扱い）
作業リポの CLAUDE.md技術規約（言語・テスト・ビルド・コーディング規約）

CLAUDE.md と Skill（.claude/commands/）の分担は「制約は CLAUDE.md、手順は Skill」。CLAUDE.md は毎ターン全文が載るので常時効かせる制約だけを置き、Skill は呼ばれたときだけ載るので長い手順を置く。

見直し予定

この運用は 2026-09-09 に始め、2026-10-07 に 1 か月分（12 案件・30 エントリ）を見直した。

  • 3 節の書式は維持する。/done の不具合追跡が 4 セッションにまたがり、CASE.md だけで続けられた。記録漏れは 30 エントリ中 1 件。ただし「見送った案」を書いていない案件が 11 件中 5 件あり、仕様変更のときに効く節なので意識して残す
  • INDEX.md の自動生成は見送る。12 件で閾値の 10 件を超えたが、手書きの負担は /done ごとに 1 行で、進行中の一覧は hook が CASE.md から生成している。「完了（〜へ統合）」のような注記も手書きだから残せる。負担が出たら再検討する
  • 合わなかった点は引き続き運用を扱う案件の CASE.md に追記する。それ自体が次の改善材料になる
  • 会社 Org への移行タイミングは未決
  • hook は 2 つとも継続する。SessionStart が進行中案件と前回の /done 漏れを表示し、SessionEnd が「未コミットの変更があるのに CASE.md が未更新」を検知して次回に持ち越す。1 か月で煩わしさの記録はない
  • Stop hook は使わない。応答を終えるたびに発火する仕様で「セッションの終わり」を判定できないため、目的に合わない
  • private/ の git add を止める PreToolUse hook は作っていない。.gitignore で足りるため（git add -f を自分で叩かない限り不要）

設計の経緯と見送った案は docs/000-design.md にある。
