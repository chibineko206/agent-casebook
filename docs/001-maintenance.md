# 保守と利用の運用ルール

このリポ（agent-casebook）を「仕組みの正」とし、日々の記録は別の非公開リポで行う前提での運用ルール。
読み手は保守する本人。主題は「仕組みの変更をどこで行い、どう配り、何を記録するか」の 1 点。

## 結論

**仕組みはこのリポでしか変えず、日々使うリポは取り込むだけにする。** 変更の流れを一方向に固定すると、二重管理と食い違いが起きない。

## 1. 役割の固定

| | agent-casebook（このリポ） | 日々使うリポ（非公開） |
|---|---|---|
| 役割 | 仕組みの正。公開候補 | 日々の利用。案件の記録 |
| 変えるもの | `CLAUDE.md`、`.claude/`、`tools/`、`templates/`、`docs/` | `cases/`、`INDEX.md`、`private/` |
| 記録の置き場 | 仕組みの開発記録を自分の `cases/` に書く（例: `cases/dev-dashboard/`）。公開されるので、業務や個人の話は書かない | 運用の実感と「どの版を取り込んだか」を運用案件（例: `cases/casebook-ops/`）に書く |
| git の作者 | 個人アカウント | そのリポの所属に合わせる |

仕組みの開発は、このリポを Claude Code で開いて行い、`/done` もこのリポの中で締める。自分の仕組みで自分を記録するので、公開リポの `cases/` がそのまま使用例になる。

## 2. 変更の流れ

1. 仕組みの改修はこのリポで行い、動作確認してタグを打つ（`v0.1.0` から。互換性を壊す変更はメジャーを上げる）
2. 日々使うリポに取り込む。取り込みは「対象ファイルの一覧を持つコピー用スクリプト」1 本で行い、取り込んだ版をそのリポの運用案件に記録する
3. 使っていて不具合に気付いたら、日々使うリポで直したくなっても、このリポで直して取り込み直す。急ぎで手元を直した場合は、その日のうちに同じ変更をこちらに入れる

submodule や subtree は使わない。取り込み対象は 20 ファイル程度なので、コピーで足り、履歴の絡みも避けられる。

**移行措置（切り出し時に残っていた改修に限る）。**このリポを切り出した時点で日々使うリポに残っていた全体影響の改修（`CLAUDE.md` の軽量化、`/done` の決定的処理のスクリプト化、生成し直せる成果物を追跡しない規則、配置を揃える作業）は、実データのある日々使うリポで対処し、完了のたびにこのリポへ書き出す。条件は 3 つ。

- 配置を先に揃えておく（3 章）。揃っていれば書き出しはファイルのコピーで済む
- 完了のたびに書き出し、`tools/check-public.sh` を通す。溜めない
- 判断の要約（なぜそうしたか、見送った案）を、書き出し時にこのリポの運用案件（`cases/casebook-ops/`）へ書く。日々使うリポの記録は業務の文脈を含むので、そのままは写さない

これらが片付いたら移行措置は終わり、日々使うリポでは全体の調整を行わない。以後の改修はすべてこのリポで行い、日々使うリポは 1 ユーザーとして取り込むだけになる。公開向けの整備（README、文書の体裁、ライセンス）は最初からこのリポで直接行う。

取り込み対象は次のとおり。日々使うリポの固有ファイル（`INDEX.md`、`cases/`、`.claude/settings.local.json`）は対象外。

```
CLAUDE.md
.claude/settings.json
.claude/hooks/
.claude/commands/
tools/
templates/
docs/manual.html
docs/chat-writeback-prompt.md
```

## 3. 配置を揃える

取り込み先の配置はこのリポと同じにする。スクリプトは `tools/`、URL スキームは `casebook://`、Launcher は `Casebook Launcher.app`。配置が違うと取り込みのたびに差分が出る。

`tools/` のスクリプトは、`CLAUDE.md` と `.claude/` を持つ最も近い親ディレクトリをリポとみなすので、置き場所を変えても動く。

## 4. 公開前の点検

push の前に `tools/check-public.sh` を通し、0 件でなければ止める。点検するのは次の 3 つ。

- 絶対パス（`/Users/<名前>`、`/home/<名前>`）
- メールアドレス（GitHub の noreply 形式を除く）
- 手元で決めた禁止語（個人名、会社名、製品名など）。語の一覧はリポの外（`~/.config/agent-casebook/forbidden-words`）に置く。一覧そのものを公開リポに入れると、隠したい語がそこに並ぶため

`cases/` に書くときも同じ点検が効く。業務の案件はこのリポに置かない。

## 5. アカウントを混ぜない

- `git config user.name` / `user.email` はリポごとに設定する。`~/.gitconfig` に次を書いておくと、このディレクトリでは自動で個人アカウントの作者になり、切り替え忘れを防げる

  ```
  [includeIf "gitdir:~/code/agent-casebook/"]
      path = ~/.gitconfig-personal
  ```

  `~/.gitconfig-personal` に `[user] name = ... / email = <ID>+<ユーザー名>@users.noreply.github.com` を書く
- `gh` は push のときだけ `gh auth switch --user <個人アカウント>` で切り替え、終わったら戻す

## 6. 判断の置き場

同じ話を両方のリポに書くと後で食い違う。線引きは次のとおり。

- **仕組みの判断**（書式、hook の挙動、ダッシュボードの項目、見送った案）→ このリポの `cases/` と `docs/`
- **運用の判断**（取り込んだ版、手元で困ったこと、こちらへ出す改善提案）→ 日々使うリポの運用案件

## 7. 依存先の記録

`tools/dashboard.py` が読むセッション記録（`~/.claude/projects/`）と、hook が受け取る入力は Claude Code の内部仕様で、予告なく変わる。壊れたら直す前提とし、README の「動作確認した Claude Code のバージョン」を取り込みのたびに更新する。

## 8. 最初の 1 回だけの作業（取り込み先ごと）

- 配置を揃える（3 章）。既存のスクリプトを `tools/` に移し、URL スキームと Launcher を置き換える
- 取り込みと書き出しのスクリプトを作る。これは取り込み先の固有物なので、このリポには入れない。対象ファイルの一覧（2 章）を両方向で共有する
- 運用案件を起こし、取り込んだ版を記録する
