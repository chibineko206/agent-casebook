# 個人共通ルール

全リポジトリに共通する作法だけを書く。
リポ固有の運用手順や技術規約は各リポの `CLAUDE.md` に置き、ここには重複させない。

## 応答

- 日本語で応答する
- 「文書の書き方」の原則は応答にも適用する。特に結論を先に書き、前置きや同じ内容の言い換えを重ねない
- 分からないことは推測で埋めず、そう言う
- ファイルを作成・更新したら、応答の末尾に「作成・更新したファイル」としてパスを必ず列挙する
  （リポジトリルートからの相対パス。1 件でも省略しない。Artifact として公開した場合は URL も併記する）

## 文書の書き方

『理科系の作文技術』（木下是雄）の要点を採る。厳密な適用ではなく、次の点を守る。
仕上げ時の点検は `~/agent-casebook` の `/doc-check` で行う。

- 読み手を決め、文書の主題を 1 つに絞る。主題は一文（目標規定文）で言えること。必要なことは漏れなく、不要なことは書かない
- 結論を先に、概観から細部へ。リード文だけで趣旨が分かるようにする
- 一段落一主題。段落の冒頭にその段落の主張を置く
- 一文一義で短く。主語と述語を対応させ、修飾語で脇道に逸れない
- 事実は断定、意見は「〜と考える」と明示する。責任を曖昧にするぼかし言葉を使わず、二通りに読める文を書かない

## 作業の起点

- 作業は issue 番号を起点にする。番号が無い依頼は、まず起票するか確認する
- Claude への指示と成果物の運用記録は `~/agent-casebook` に集約している
  （運用手順の詳細は同リポの `CLAUDE.md` を読む）
- チケット管理（Jira など）がある案件はそちらを正とし、GitHub issue にはそのキーを併記する

## 確認が必要な操作

次の操作は、その場で許可を得てから実行する。過去に一度許可されたことを次回の根拠にしない。

- `git commit` / `git push` / ブランチやタグの削除
- 作業ツリーの変更を消す操作（`git restore` / `git checkout -- <file>` / `git stash` / `git reset`）
- issue・PR の作成やコメント、クローズ（外部に残る操作）
- ファイルの削除、上書き（上書き前に必ず中身を確認する）
- 外部サービスへのデータ送信

## コード変更

- 既存コードの書き方（命名・コメント量・イディオム）に合わせる
- ユーザーは会話中にファイルを直接編集することがある。編集前に必ず現在の内容を読み直し、全文上書きではなく部分編集を使う
- 頼まれた範囲を勝手に広げない。気付いた別の問題は報告して判断を仰ぐ
- テストが失敗したら、出力を添えて失敗したと報告する。通ったことにしない
